Which pages should you refresh first? A validated decline-risk model for content teams

Refresh / Content Opportunity Scoring lane · September 2026
Abstract. Which of a content team's existing pages should be prioritized for review this week, using only observed search and content signals? I built a decline-risk classifier on the FlyRank ML Internship starter dataset (30,000 pseudonymized pages, 32 clients) and compared it against a transparent rule-based baseline on an identical client-held-out split. Logistic regression reached a precision@50 of 0.74 versus the baseline's 0.48 (base rate 0.517) while staying interpretable, and two deliberate stress tests — a naive random split and a reintroduced label-derived feature — each showed how easily that number can be overstated if validation is sloppy. The output is a ranked, reason-coded action queue meant for a human reviewer's weekly triage, not an automated publishing decision.

Introduction & Problem Statement

A content team reviewing hundreds or thousands of existing pages can't manually check every one every week. The decision this work supports is narrow and practical: given a limited review budget, which pages should a human look at first? The unit of analysis is one content page, belonging to one pseudonymized client. The output is a ranked queue with a risk score, an action label, and a plain-language reason — not an automated publish, unpublish, or de-index decision.

A wrong call has a real, if modest, cost either way: a false positive wastes reviewer time on a page that wasn't really at risk; a false negative lets a genuinely declining page go unreviewed, and lost search visibility gets harder to win back the longer it's ignored. A single hand-written rule can combine two or three signals; the pattern that actually separates a declining page from a stable one usually involves several signals at once (traffic level, position, freshness, depth) — which is where a learned model can help, provided it's validated honestly enough to trust.

Data

Source: the FlyRank ML Internship starter release — 30,000 pseudonymized content pages across 32 pseudonymized clients, every metric aggregated over a trailing 90-day window ending at export time. No client names, domains, URLs, credentials, or raw search queries appear anywhere in this analysis.

Deliberately excluded, and why

  • trend_direction, trend_pct — the label is computed directly from these; including them would be circular.
  • impressions_last_30d / impressions_prev_30d (and their clicks/sessions twins) — their difference is the label. Re-adding just two of these columns as a test moved ROC AUC from 0.625 to 0.846 — a clean confession of label leakage.
  • content_id, client_id — pseudonyms, used only for grouping and splitting, never as model inputs.
  • provider_used, model_used — explicitly out of scope per the data dictionary.

Methodology

Label: target_declining = 1 when trend_direction == "down" — a 30-day-vs-previous-30-day impressions swing, treated throughout as a proxy for "at risk," never a verified outcome.

Baseline: a transparent, no-fitted-weights rule — stale × visible × impressions plus a bonus for page-one pages pulling below-median CTR for their position — with both thresholds fit on training clients only and frozen before scoring the held-out test clients. (An earlier version that fit thresholds on the same data being scored inflated precision@50 to 0.88; fitting on train only is the honest number used everywhere below.)

Features: trailing-90-day counts (log-transformed), CTR, average position (with a flag for FlyRank's "no data" zero-rows), content age, days since update, keyword context, content depth — with explicit missingness flags rather than silent zero-filling.

Models: logistic regression, a shallow decision tree, random forest, and gradient boosting — testing whether extra complexity earns its place rather than assuming it does.

Validation: grouped by client (25% of clients held out, zero client overlap between train and test) — the honest question is "does this work for a client the model has never seen," not "can it memorize this client's typical traffic level."

A 20-point gap, from letting a client's other pages leak into training. The headline number in this paper is the honest one.

Leakage audit

Deliberately adding back impressions_last_30d / impressions_prev_30d — columns whose difference defines the label — moves ROC AUC from 0.625 to 0.846. That jump toward a near-perfect score is the textbook confession described in this project's leakage-hunting process; those columns stay out of the real model.

Interpretation

Permutation importance on the winning model: overall traffic volume (log_impressions_90d, log_clicks_90d, log_users_90d) dominates, with avg_position a clear second. This is a sane, non-circular story: lower-traffic pages have noisier 30-day counts, so they cross the trend threshold more easily — the model has partly learned "which pages are volatile enough to swing." No single feature pushed AUC anywhere near 1.0 alone, which is the leakage smell test coming back clean.

Error analysis: false positives (flagged as declining, actually not) sit at a higher median impression volume than false negatives or correct predictions — the model over-flags some large, stable pages. False negatives concentrate in low-traffic pages, exactly where the 30-day trend proxy is noisiest — some of this "error" is a proxy-label ceiling, not a pure modeling gap.

Limitations & Honest Framing

  • Proxy label, not ground truth. The target is a 30-day-vs-30-day impressions swing, not a verified business outcome.
  • No causal claim. This ranks decline risk; it does not show that refreshing a flagged page will fix it, and nothing here predicts or reverse-engineers Google's ranking algorithm.
  • Validated on 32 clients, one snapshot. No time-based validation was run; claims about future periods or unseen client types are unsupported.
  • Split choice changes the headline number by 20 points — a reminder that any single precision@K figure is only as honest as the split behind it.
  • Decision-support only. Output is a ranked queue for a human reviewer, never an automated action.

A reviewer works the queue top-down by score. Before acting on any flagged row, a human should confirm the position data is real (not FlyRank's "no data" zero), rule out a seasonal or one-off traffic dip, and consider whether the page's content type makes a refresh worthwhile at all. This output should never trigger automated publishing, editing, or de-indexing, and should never be used to compare one client's content team against another's.
